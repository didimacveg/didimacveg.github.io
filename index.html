RAAN Open Orbital Intelligence Lab

Flagship · research project

An open, reproducible lab on public orbital data: a digital twin of the catalogue, a collision-risk study on ESA's dataset and a manoeuvre detector, each with its baseline reproduced first and its negative results published. A research project, not an operational service.

Screenshots of the RAAN web app, run of 12 November 2026. The app has a light interface; lightness is inverted here to sit on this page. Nothing else is edited.

Question
How far can public data alone take you in space situational awareness, and how do you know when a model is really better than doing nothing? Orbit visualisers always look plausible and machine-learning scores are easy to flatter. The lab's rules: public data only, every number regenerated by one command, baselines reproduced before any model is trained.
Modules
  • Orbital digital twin. A WebGL globe of every object with public bulk elements, SGP4 running in a Web Worker, filters, a time bar and a provenance card per object.
  • Collision research lab. ESA's Collision Avoidance Challenge dataset: the naive forecast reproduced, then gradient boosting and a recurrent network scored with the official metric, bootstrap intervals, calibration and a bias analysis.
  • Manoeuvre detection. A physics step detector, CUSUM and a gradient-boosted classifier on 15 satellites whose operators publish their burns, evaluated leave-one-satellite-out.
  • Reports. Small deterministic programs fill report templates from pipeline outputs; a number guard rejects any figure not backed by a cited fact.

Cross-validation says the opposite (0.98, and 1.23 nested, against 0.80) and it wins only 86 % of bootstrap resamples. The GRU (1.32) and direct regression (2.37) are worse than doing nothing.

Limits
The catalogue covers only objects with public bulk elements (most debris needs a Space-Track account). The detector design was tuned on the same 15 satellites it is scored on. Frame rate was measured with software rendering only, not on a real GPU or phone. 62 Python tests and 7 web tests pass.

Syndrome Lab Quantum error correction

In progress

Neural decoders vs minimum-weight perfect matching on the surface code, built with Stim and PyMatching. Results and report to be published late November 2026.

Question
A quantum computer only works if errors are decoded faster than they accumulate. Minimum-weight perfect matching (MWPM) is the standard decoder for the surface code. When, if ever, does a neural decoder beat it, and at what cost?
Rules
The same as RAAN: reproduce the MWPM baseline first, compare every decoder under one protocol, and publish the result whichever way it goes.

gravity-lab

C++17 · validated

An N-body simulator of the Solar System, checked against astronomical measurement rather than eyeballed.

Problem
An orbit simulation always looks plausible. A poor integrator invents effects of its own: at a careless time step this code manufactures 67″ per century of spurious perihelion precession, more than the relativistic effect I wanted to measure. Without validation, a pretty animation proves nothing.
Solution
  • Real J2000 initial conditions (planets, dwarf planets, comets) in 3D, barycentric frame.
  • Four integrators compared head to head; the default is Yoshida 4, a fourth-order symplectic method, because its energy error stays bounded instead of drifting.
  • First post-Newtonian correction and solar J2; a black-hole module with an ISCO-based capture criterion; adaptive sub-stepping for close encounters.
  • A validation suite that tests conservation laws, convergence order and Kepler's third law on simulated orbits, run in CI on every push.

KAIROS

Python · local-first

A modular, local-first personal AI assistant that talks, remembers, acts on my desktop and proposes changes to its own code.

Problem
Cloud assistants know nothing about my context and send what they do learn to someone else's servers; local ones run privately but know nothing about me. I wanted one that does both, keeps working without internet, and can never execute something it invented.
Solution
  • A core plus specialised agents (voice, memory, reasoning, documents, automation), each a bounded context behind one contract.
  • Hybrid language model: cloud reasoning with automatic fallback to a local model when there is no internet.
  • Desktop control through a closed whitelist: the model chooses actions, it never writes commands.
  • Self-improvement pipeline: it writes a patch, tests it in a network-less sandbox, and leaves a proposal; a separate service merges it only after my approval.

Chess trainer

Personal tool · private

A local training app for deliberate chess practice: understanding why a move works, not memorising it.

Problem
Most training tools tell you the best move but not why, don't know which mistakes you keep making, and generate explanations that sound right without being checked.
Solution
  • An adaptive diagnostic (Glicko-2 per skill area), analysis of my own games with lichess-style move classification, a thinking routine (threat, candidates, move), calculation without moving pieces, tactics, openings, pawn structures, endgames and play against Stockfish or Maia, a network trained to play like humans of a given rating.
  • Every explanation is built from verifiable facts (Stockfish, endgame tablebase or board rules); a test checks that each sentence cites a fact and that every move, square or number it mentions is in that fact.
  • Spaced repetition (FSRS) brings mistakes back at the right time; runs locally, no accounts.
